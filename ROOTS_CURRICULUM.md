# Курс "Корни" — 600 корней с теорией, практикой и растущими текстами

Дизайн-документ от 2026-09-11. Автор концепции — пользователь; структура
теории и разбор рисков — Claude. Статус: **обсуждается, не начато**.

## Идея в одном абзаце

600 самых частотных корней иврита, по частотности, разбиты на 3 базы по
200 ("1ые 200 корней", "2ые 200 корней", "3ие 200 корней"). Для каждого
корня — страница теории (разбор нейронкой, структура ниже) и 20 частотных
предложений с словами этого корня. Отдельная страница ведёт пользователя
по циклу теория → 20 предложений → теория → 20 предложений, корни
открываются строго по порядку; когда предложения корня пройдены, они
добавляются/открываются в соответствующей базе. Каждые 3 пройденных
корня — сгенерированный текст, использующий в основном уже изученные
корни. Часть текстов, которые получаются похожими на настоящие книги,
добавляются в библиотеку читалки **вручную** (автоматический критерий
"похоже на книгу" решили не строить — небыстро, не окупается).

**Решение по объёму (2026-09-11, после обсуждения рисков)**: начинаем
только с первой базы (200 самых частотных корней) — там живёт основная
польза по ресёрчу (50-100 корней уже дают большой прирост понимания, 600
— за гранью окупаемости на старте). Базы 2 и 3 — на будущее, архитектура
их не исключает, но контент под них не генерируем сейчас.

## Как базы встраиваются в существующую архитектуру

Три базы корней — это **обычные уровни в существующей системе пулов**
тренажёра (`progress.pool.levels`/`include`/`exclude`, тот же механизм,
что уже переключает алеф/бет/гимель) — не новая подсистема хранения.
Каждая база **всегда может быть выключена** пользователем тем же
переключателем уровня, что и обычные уровни сейчас. Предложения корня
физически появляются в пуле (через `appendCustomCards`-подобный
append-only механизм — см. project_hebrew_trainer_login.md про то, почему
DATA-позиции никогда не переставляются) только после того, как
пользователь прошёл теорию И 20 предложений этого корня — до этого момента
предложения корня просто не существуют в его локальной базе.

## Пайплайн данных

1. **Частотный список корней** — тот же подход, что описан в MARKETING.md
   для рынка, только для данных: взять открытый частотный список слов
   (напр. teachmehebrew, 10000 слов) → прогнать через Gemini (тот же
   подход, что `5_gemini_pipeline.py`) → определить корень каждого слова →
   просуммировать частоты по корням → взять топ-200 (было топ-600, сузили
   вместе с объёмом всего курса). Реальная частотность, не список
   неизвестного происхождения.
2. **Теория по каждому корню** — см. структуру ниже, генерируется один раз
   на корень.
3. **20 предложений на корень** — частотные, естественные, с реально
   употребимыми производными этого корня (не гипотетическими формами по
   всем 7 биньянам сразу — см. "Риски" про Arad 2005).
4. **Растущие тексты** каждые 3 корня — отдельный, менее детерминированный
   генеративный шаг (см. "Риски" про то, почему это самое узкое место).

## Предлагаемая структура теории (черновик, на обсуждение)

Основана на находках ресёрча (см. предыдущее сообщение в чате): корень не
предсказывает значение на 100% по всем биньянам, поэтому теория должна
показывать РЕАЛЬНО употребимые производные, а не гипотетическую полную
таблицу.

1. **Корень + один тезис-интуиция** ("שׁ-מ-ר — вокруг идеи охраны,
   сохранения") — явно как интуиция-подсказка, не строгое правило.
2. **2-4 реальных, частотных производных слова** этого корня — только те
   биньяны, что реально употребимы для ЭТОГО корня (не все 7 гипотетически).
   На каждое: слово с огласовками, биньян, часть речи, перевод, один
   пример употребления.
3. **Честная пометка расхождений** — если какое-то производное значит
   что-то не по интуиции из пункта 1 (а такое бывает часто — см. Arad),
   явно это отметить, а не замалчивать.
4. **Мнемоника** (опционально) — переиспользовать существующий паттерн
   иллюстраций-подсказок из читалки, если применимо для абстрактных
   корней.
5. Переход к практике: "Теперь увидим этот корень в реальных
   предложениях."

## Страница курса (флоу)

Теория корня 1 → 20 предложений в тренажёре (пул этого корня) → теория
корня 2 → 20 предложений → теория корня 3 → 20 предложений → **текст**
(использует в основном корни 1-3) → теория корня 4 → ... Предложения
конкретного корня становятся доступны в базе тренажёра только после
прохождения его теории (гейтинг).

## Переток в читалку

Тексты, которые получаются похожими на настоящую историю (не просто
набор тренировочных фраз), добавляются в библиотеку читалки как обычная
книга — вручную, решение "похоже на книгу или нет" принимает человек, не
код. Естественное развитие механики "macaronic fade" (постепенное
замещение перевода на иврит), которая там уже есть.

## Риски (из обсуждения перед стартом, 2026-09-11)

- **Растущие тексты — самое узкое технически место.** Чем больше корней
  накопилось, тем сложнее модели писать естественный, связный текст,
  который "в основном" использует уже пройденные корни — реальный риск
  словарного, неестественного текста, который формально удовлетворяет
  условию. Та же ловушка "формально верно, реально плохо", что уже ловили
  в проекте на никуде/иллюстрациях/произношении — ожидать того же самого
  здесь и закладывать время на ручную проверку именно этих текстов.
- **QA на объёме.** Даже на суженных 200 корнях × 20 предложений = 4000
  новых предложений — это половина текущего корпуса тренажёра. Глазами
  всё не проверить, полагаться на точечные проверки + перенос уже
  наработанных QA-привычек (как `8_audio_qa.py` у читалки).
- **Дедуп с существующими 8239 предложениями тренажёра** — не
  координируется автоматически, риск пересечения лексики/контента.
  Решить перед генерацией: сверять при генерации, или принять пересечение
  как есть.
- **Состояние гейтинга (какая теория пройдена) — новое состояние**,
  которого пока нет ни в localStorage, ни в схеме Firestore. Нужно
  спроектировать sync по аналогии с уже существующими полями прогресса
  (`progress.pool`/`meta`), не как отдельную систему.
- **Дневная квота Gemini — подтверждено вживую, не гипотеза.** Прогон
  `build_root_frequency_list.py` (2026-09-11) упёрся в лимит free tier
  `gemini-3.6-flash` — **20 запросов/сутки** — на 320 из 650 слов (после
  увеличения батча до 150 слов/запрос это ~5 запросов на весь список, то
  есть должно укладываться в сутки; при исходном батче 40 не влезло).
  Для теории (200 запросов, по одному на корень) и предложений (тоже
  минимум 200 запросов, по одному на корень, если не собирать в батчи) в
  лоб это **10+ дней** только на API-вызовы, даже без сбоев/некачественных
  ответов. Явно закладывать это в оценку сроков, батчить максимально
  крупно (несколько корней теории/предложений за один запрос, не один
  корень на запрос), и/или обсудить платный тир, если хочется быстрее.

## Шаг 1 — готово: скрипт для частотного списка корней

- `hebrew_word_frequency_1_650.json` — 650 реальных слов современного
  иврита, ранжированных по частоте (teachmehebrew.com/hebrew-frequency-list.html,
  верхняя часть их списка на 10000 слов). Взяты именно топ-650, а не всё
  десять тысяч — по закону Ципфа самые частотные КОРНИ уже видны в первой
  тысяче слов, а длинный хвост частотный список корней почти не меняет.
- `build_root_frequency_list.py` — питон-скрипт по образцу
  `5_gemini_pipeline.py`: берёт этот список, батчами прогоняет через
  Gemini (определить корень каждого слова или "нет корня" для служебных
  слов), затем **локально в Python** (не нейронкой — детерминированный
  подсчёт) агрегирует по корням: скор корня = сумма 1/rank по всем его
  словам в списке (частотно-взвешенно, не просто счётчик). Есть
  `--resume`, как у остального пайплайна книг.
- **Не запускал** — нет ключа Gemini в этой сессии (BYOK, как и весь
  остальной пайплайн). Запустить: `export GEMINI_API_KEY=...` и
  `python3 build_root_frequency_list.py hebrew_word_frequency_1_650.json`.
- Если после обработки корней получится МЕНЬШЕ 200 (вероятно — многие из
  650 слов служебные, без корня, скрипт предупредит об этом явно) —
  нужно либо взять из teachmehebrew ранги 651+, либо принять базу меньше
  200 на первый заход.
